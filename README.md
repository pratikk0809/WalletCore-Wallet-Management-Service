# Wallet & Transaction Service

[![CI](https://github.com/pratikk0809/WalletCore-Wallet-Management-Service/actions/workflows/ci.yml/badge.svg)](https://github.com/pratikk0809/WalletCore-Wallet-Management-Service/actions/workflows/ci.yml)

A backend wallet and transaction service (a mini fintech core) built with FastAPI, PostgreSQL, SQLAlchemy 2.0 and Alembic. It focuses on getting money handling right: a double-entry ledger, idempotent requests, row-level locking, an audit trail, and database-enforced rules.

**Out of scope (v1):** real payment gateways, KYC, currency conversion, any UI.

## Features

- **Accounts:** register (a wallet is created in the same DB transaction) and log in with JWT (OAuth2 password flow, Argon2 password hashing).
- **Money movement:** deposit, withdraw and wallet-to-wallet transfer, each with exact `Decimal` amounts, a per-transaction min/max and a daily outgoing limit.
- **Idempotency:** every money request needs an `Idempotency-Key`. A retry returns the original result and never moves money twice.
- **Double-entry ledger:** every transaction writes balanced ledger entries with a running `balance_after`; wallet balances always reconcile with the ledger.
- **History and statements:** cursor-paginated transaction history with filters, and a per-period statement with opening/closing balance.
- **Audit log:** registrations, logins (including failures), money operations and admin actions are recorded in the same DB transaction as the action.
- **Admin:** freeze or unfreeze a wallet (admin role only).
- **Hardening:** rate limiting (429 + `Retry-After`), Postgres triggers that make the ledger, audit log and completed transactions immutable, a consistent error format with request IDs, structured JSON logs.

## Quick start

Requires Docker Desktop (running).

```bash
git clone https://github.com/YOUR-USERNAME/wallet-service.git
cd wallet-service
cp .env.example .env          # Windows PowerShell: copy .env.example .env
```

Generate a secret key and put it in `.env` as `SECRET_KEY=...` (the app refuses to start with a short or missing key):

```bash
python -c "import secrets; print(secrets.token_hex(32))"
```

Start the app and create the tables:

```bash
docker compose up --build
docker compose exec app alembic upgrade head
```

Open **http://localhost:8000/docs** for the interactive API reference.

### Create the first admin

There is deliberately no API for this. Register a user first, then:

```bash
docker compose exec db psql -U wallet -d wallet_db -c "UPDATE users SET role = 'admin' WHERE email = 'you@example.com';"
```

## Configuration

All settings come from environment variables (see `.env.example`). The important ones:

| Variable | Default | Meaning |
|---|---|---|
| `DATABASE_URL` | required | SQLAlchemy URL (`postgresql+psycopg://...`) |
| `SECRET_KEY` | required, 32+ chars | JWT signing key |
| `ENVIRONMENT` | `local` | `/docs`, `/redoc` and `/openapi.json` are served only when `local` |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | `30` | Token lifetime |
| `MIN_TRANSACTION_AMOUNT` / `MAX_TRANSACTION_AMOUNT` | `0.01` / `100000.00` | Per-transaction limits |
| `DAILY_LIMIT` | `50000.00` | Max a wallet may send out per UTC day (withdrawals + transfers) |
| `LOGIN_RATE_LIMIT` / `REGISTER_RATE_LIMIT` | `10` / `5` | Requests per window, per client IP |
| `MONEY_RATE_LIMIT` | `30` | Deposit + withdraw + transfer requests per window, per user |
| `RATE_LIMIT_WINDOW_SECONDS` | `60` | Rate-limit window |

## API summary

Full details, examples and error formats are in the interactive docs at `/docs`.

| Method | Path | Purpose |
|---|---|---|
| GET | `/health` | Liveness and database check |
| POST | `/auth/register` | Create an account and its wallet |
| POST | `/auth/login` | Log in (form fields `username` = email, `password`) |
| GET | `/wallets/me` | Your wallet and balance |
| GET | `/wallets/me/limits` | Daily limit usage |
| GET | `/wallets/me/statement` | Ledger statement for a period |
| POST | `/wallets/deposit` | Add funds |
| POST | `/wallets/withdraw` | Withdraw funds |
| POST | `/transfers` | Send money to another wallet by wallet ID |
| GET | `/transactions` | History (filters, cursor pagination) |
| GET | `/transactions/{transaction_id}` | One transaction |
| POST | `/admin/wallets/{wallet_id}/freeze` | Freeze or unfreeze a wallet (admin) |

Conventions:

- **Money** is a string with at most 2 decimals (`"250.75"`), never a float. Amounts that don't fit are rejected, never rounded.
- **Idempotency:** `Idempotency-Key` header (1-64 chars: letters, digits, `.`, `_`, `-`). `201` = new, `200` + `Idempotent-Replayed: true` = replay, `409` = same key with a different request.
- **Errors** always look like `{"error": {"code", "message", "request_id"}}` (validation errors add `details`). Quote the `request_id` when reporting a problem.

## Architecture

Strict layering: **API → Service → Repository → DB**. Each layer talks only to the one below it.
Diagrams of the layers, the deposit flow, transfer locking, the ledger model and the schema are in [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

- `app/api/`: HTTP only (parse, call a service, return). No business logic. `deps.py` is the single place where repositories are wired into services.
- `app/services/`: all business rules. Never import FastAPI. A service call is one DB transaction and the service owns the `commit()`.
- `app/repositories/`: SQL only. They `flush()` but never commit.
- `app/models/`, `app/schemas/`: SQLAlchemy models and Pydantic request/response shapes.
- `app/core/`: settings, security, money validation, idempotency hashing, pagination, rate limiter.
- `app/exceptions/`: business errors plus the global handlers that turn them into HTTP.

## Key design decisions

| Topic | Decision |
|---|---|
| Money | `NUMERIC(18,2)` in the database, `Decimal` in Python, strings in JSON. |
| Ledger | Double entry. A deposit is credit wallet + debit "external" (an entry with no wallet), so there is no hot system wallet and `CHECK (balance >= 0)` stays strict. A transfer is debit source + credit destination. |
| Concurrency | The wallet row is locked (`SELECT ... FOR UPDATE`) before the balance is read. Transfers lock both rows in ascending ID order, so opposite transfers cannot deadlock. |
| Idempotency | Key unique per `(user, key)` with a hash of the request. The lock is taken first, then the key is checked; the unique constraint is the backup. |
| Immutability | Postgres triggers reject `UPDATE`/`DELETE` on the ledger and audit log, and any change to completed transactions. Corrections must be new transactions. |
| Audit | Written in the same DB transaction as the action, so an action and its audit row succeed or fail together. No emails or secrets are stored. |
| History | Cursor pagination on `(created_at, id)`, stable while new transactions arrive. |
| Security | Argon2 hashing, pinned JWT algorithm, identical error for wrong password and unknown email, UUID identifiers, 404 (not 403) for other users' transactions, admins created only by SQL. |

## Known limitations

- **Rate limiting is in memory,** so counters are per process. Several workers need a shared store such as Redis.
- **Client IP** is `request.client.host`. `X-Forwarded-For` is not trusted because clients can fake it, so behind a reverse proxy the proxy's address is used.
- **The daily limit uses UTC days,** not the user's timezone.
- **Rejected attempts** (insufficient funds, frozen wallet, limit exceeded) are logged but not stored.
- **One wallet per user, one currency (INR).** Multi-currency, reversals/refunds and webhooks are not implemented.
- **Idempotency keys are kept forever.**

## Deployment notes

Before running this anywhere public:

- Set `ENVIRONMENT` to something other than `local` (turns off `/docs`, `/redoc` and `/openapi.json`).
- Use a strong, unique database password and a freshly generated `SECRET_KEY`. Never reuse the example values.
- Run the app with a limited database role and `REVOKE UPDATE, DELETE, TRUNCATE` on `audit_logs`, `ledger_entries` and `transactions`, so the triggers are not the only protection.
- Put the app behind HTTPS, and decide how to trust a reverse proxy before relying on client IPs.
- Run the API with several workers only after moving the rate limiter to a shared store.
